How it works

A change goes all the way round before anyone is asked to merge it.

A project holds a timeline and its milestones. A WorkOrder is one piece of that work, and this is the loop it runs.

  1. 01

    Plan

    A planning agent projects the timeline and the relative size of each milestone from the goals you state, so there is a schedule to dispatch against.

  2. 02

    Dispatch

    The orchestrator starts WorkOrders at the token flow rate you set. It drives the Claude Code and Codex CLIs, so the work runs on the subscription you already have.

  3. 03

    Implement

    Each WorkOrder gets its own git worktree branched from your default branch. The agent works there, commits, and opens the pull request.

  4. 04

    Review

    A reviewer that cannot write reads the diff and the code around it, then leaves every finding inline on the pull request — including when it finds nothing.

  5. 05

    Decide

    The run stops on a human review step and Slack tells you it is waiting, with a link to the pull request. Approving or rejecting is yours, always.

Workflows as code

Your SDLC, written down once.

Workflows live in your repository as zero-dependency Python. A definition is compiled at startup and snapshotted onto every run, so editing the file never changes a run already in flight. 

workflow = oe.workflow(
    id="implementation-review-v1",
    workspace=oe.workspace(),
    steps=[
        oe.agent_step(
            id="implementation",
            agent=implementation_agent,
            workspace_access="write",
            required_outputs=["pr_url"],
            transitions={"success": oe.goto("review"), "*": oe.fail()},
        ),
        oe.agent_step(
            id="review",
            agent=review_agent,
            # A reviewer that cannot write cannot quietly fix
            # what it was asked to report.
            workspace_access="read",
            transitions={"*": oe.goto("human-review")},
        ),
        oe.human_review_step(
            id="human-review",
            approved=oe.succeed(),
            rejected=oe.fail(),
            notification=oe.slack_notification(channel="OpenEngine"),
        ),
    ],
)

workflows/implementation_review.py — the workflow that builds OpenEngine.

What's shipped

Running today, in the open.

OpenEngine builds itself with the loop above. Everything here is in the repository now, not on a roadmap.

Approvals

One policy, both runners

Capabilities — read, edit, bash, web, mcp — plus per-command shell globs where deny outranks ask outranks allow. Preapproved work never interrupts you; anything the policy has not ruled on is put to a person.

Portability

The conversation is yours

History lives in OpenEngine's own store, not in a vendor's session. A provider session is an optimisation, so one runner can pick up where another stopped.

Graph WorkOrders BETA

LangGraph, when a graph fits better

Graph workflows sit beside the step-based ones in the same directory and start on the graph engine, with their progress reported the same way.

Durability

Work outlives its checkout

A workspace is a durable branch plus a worktree you can detach and reattach. A supervised local Temporal service keeps runs going across restarts.

GitHub

Connected in six steps

OAuth device flow, tokens in your OS keychain, refreshed automatically when they expire. OpenEngine opens the pull requests and posts the review comments.

Interface

Start it anywhere, read it later

A web control interface with projects, milestone timelines, WorkOrders, and approvals answered inline — from a laptop or a phone on the same network.

Why

Positions we are not going to trade away.

Not coupled to any provider.

Claude Code, Codex, whatever comes next. The conversation is ours, not a vendor's, so any runner can pick up where another left off.

Workflows encode your review standards.

Stringent security reviews and checklists, defined once in your repository and applied to every change that goes through.

Your budget, your machine.

OpenEngine drives the CLIs you already subscribe to, on hardware you already own, at a token flow rate you set.

It augments your workflow; it doesn't replace it.

Every run ends at a person. You stay the one who decides what ships.
